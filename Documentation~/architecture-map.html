Palmware Lightguns · Unity package

The Lightgun Layer, on one page

Every conversation between your game and a physical gun passes through one switchboard. Game code and gun hardware never talk to each other directly — that is the whole design.

input events — flow UP to the game aim — read every frame feedback commands — flow DOWN to hardware plug-in & detection

The map — four layers

Layer 1 · your gameplay code
Shooter script · crosshair UI · options menu
Knows nothing about guns. Subscribes to the manager's events, reads AimPosition, and decides when feedback should happen (no recoil on a dry fire, for example).
▲FirePressed / ReloadPressed / GunConnected events ▲AimPosition read each frame ▼Recoil(device, ammo) · RumbleAll() · ReloadAll() · SetAmmoAll(n)
Layer 2 · the switchboard (a scene GameObject)
LightgunManager
The ONE class the game talks to. It is watching for three things:
1 · Action events Listens to Fire/Reload in LightgunInputActions.inputactions — the asset where mouse click, Blamcon trigger and RS3 trigger are all bound to the same action.
2 · Module registry Modules call Register(this) when enabled. To route a shot it asks each one: “Owns(device) — is this trigger pull yours?”
3 · Aim arbitration Every frame: “Mouse, did you move? Modules, TryGetAim?” — whoever moved last owns the crosshair.
4 · Hot-swap watch Forwards Unity's plugged-in / unplugged notices to every module, then tells the game via GunConnected/GunDisconnected.
▲Register(this) — “I exist, I handle gun X” ▼questions & orders: Owns()? · TryGetAim()? · Recoil()!

BlamconModule

driver for Blamcon guns (P1–P4)
  • Looks for: BlamconLightgunHID devices (Gamepad mode; BlamconSerial handles guns left in MnK mode)
  • Aim: the gun's absolute position control, already in screen pixels
  • Speaks: recoil / rumble / LED / ammo commands; re-arms FFB control on every re-plug
▼ USB HID output reports

RetroShooterModule

driver for the RS3 “Reaper”
  • Looks for: “3AGAME / Retro Shooter” devices + its COM port (auto-detected by USB VID/PID); MnK-first — Joystick mode (ZJ) when 2+ guns
  • Aim: joystick stick (absolute), inverted & smoothed to damp IR jitter
  • Speaks: Z0–Z5 recoil+LEDs · Z6 slide return · ZZ rumble
▼ serial COM text commands

SindenModule

compat for mouse-type guns
  • Looks for: “Sinden” in device names, plus a manual options-menu toggle
  • Aim: none of its own — the Sinden driver moves the OS cursor, so the mouse path covers it
  • Speaks: nothing to hardware; shows/hides the white SindenBorder the camera needs
▼ (no commands — Sinden's own software does feedback)
▼hardware, each speaking its own language

🔫 Blamcon lightgun

USB HID gamepad · IR 4-point tracking · kicks, buzzes, LEDs

🔫 Retro Shooter RS3

HID joystick + virtual COM port · recoil, slide, ammo LEDs

🔫 Sinden lightgun

camera in the barrel · its PC driver moves the OS mouse cursor
The Sinden loop: its hardware never talks to the game at all. Camera → Sinden driver software → OS mouse cursor → Unity Input System → back into the manager's mouse path at the top. That's why single-player Sinden support is “almost free” — and why the border overlay is the only thing we must render for it.

One shot, end to end

  1. You pull the Blamcon trigger.
  2. Unity's Input System matches it to the Fire action (binding: <LightGun>/buttonWest) and fires it with the exact device attached.
  3. LightgunManager debounces trigger bounce, then asks each module “Owns(device)?” — BlamconModule answers “mine”.
  4. The manager raises FirePressed(args) — device, owning module, and where you were aiming.
  5. Your shooter script raycasts from args.AimPosition, spends ammo, then calls Recoil(args.Device, ammoLeft).
  6. The manager routes that to BlamconModule.Recoil() → USB HID recoil command → the gun physically kicks. A mouse click stops at step 5: nothing owns it, nothing kicks.

Aiming, every frame

  1. LightgunManager.Update() asks: “Mouse, did you actually move?” — an idle mouse never steals the crosshair.
  2. Then each module: “TryGetAim?” — Blamcon reads its position control; the RS3 reads its stick and smooths the jitter.
  3. Whichever source moved most recently wins and becomes AimPosition. Your crosshair and raycasts read that one value and never know who's driving.

The golden rule this buys you: adding or swapping a gun = one new module + a row of input bindings. The manager doesn't change. Your game code doesn't change. It was never talking to the gun in the first place.
